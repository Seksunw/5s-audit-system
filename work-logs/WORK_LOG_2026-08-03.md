## 1.3 ⚠️ Bug ที่ยังอยู่ใน `js/app.js` (ยังไม่ได้แก้)

**`TRANSLATIONS` มี key `en:` ซ้ำ 2 ครั้ง**

| บล็อก | บรรทัด | สภาพ | ผล |
|---|---|---|---|
| `en:` ตัวแรก | 624–830 | แปลไม่เสร็จ ค่าเป็นภาษาไทย ~90 key | **dead code** — JS ใช้ตัวหลังทับ |
| `en:` ตัวสอง | 831–1037 | แปลครบถูกต้อง 188 key | ตัวที่ทำงานจริง |

- **ไม่กระทบการทำงาน** เพราะ JavaScript object literal ใช้ค่าที่ประกาศหลังสุด
- แต่เป็น **dead code 207 บรรทัด** ที่ทำให้เข้าใจผิดว่า EN แปลไม่ครบ
- **ควรลบบล็อกแรก (624–830) ออกเมื่อสะดวก** — ไม่กระทบอะไรเลย

**`data-i18n` บน element ที่มี `<strong>` ข้างใน** — `home.html` บรรทัด 122, 126, 130
(`home.score_ex` / `score_good` / `score_imp`) — `apply()` ใช้ `textContent`
→ **ตัวหนาของตัวเลข 90-100% / 75-89% / 0-74% หายทุกครั้งที่โหลดหน้า** (ทั้ง TH และ EN)
วิธีแก้: เปลี่ยนเป็น `data-i18n-html` แล้วย้าย `<strong>` เข้าไปในค่าคำแปล

## 1.4 งานที่ทำไปแล้วและ "ยกเลิก" (rollback)

ทำครบแล้วผ่านการตรวจทุกข้อ (404 key TH/EN ตรงกัน · ไทยหลุด 0 จุด · tag สมดุลทุกหน้า)
แต่ตัดสินใจ **ยกเลิกทั้งหมด กลับสภาพเดิม** เพราะขอบเขตงานบานปลาย

สิ่งที่ทำไปแล้วและถูกย้อนกลับ:

- แยก `js/i18n/th.js` + `js/i18n/en.js` ออกจาก `app.js` (ลด 611 บรรทัด)
- เพิ่ม MutationObserver auto-apply + missing-key console.warn + `data-i18n-attr`
- แยก semantic `data-i18n` (แปลทุกรอบ) vs `data-i18n-init` (แปลรอบแรก — element ที่ JS เขียนทับ)
- ติด attribute ~150 จุดใน 14 หน้า · แทน hardcode 113 จุดใน `app.js`
- bump `sw.js` → `v4.7`

### 🔑 บทเรียนสำคัญที่ได้ (ถ้าจะทำ i18n รอบใหม่ ต้องรู้)

**พบตอนทำแล้วเกือบพลาด** — ถ้าเพิ่ม MutationObserver ให้ `apply()` รันซ้ำทุกครั้งที่ DOM เปลี่ยน
จะมี **24 element ที่ถูกทับข้อมูลจริงกลับเป็นข้อความตั้งต้น** ต้องแยกเป็น `data-i18n-init`:

| element | JS ที่เขียนทับ |
|---|---|
| `.loading-msg` (ทั้ง 14 หน้า) | `UI.showLoading(msg)` → ข้อความเฉพาะเด้งกลับเป็น "กำลังโหลด..." |
| `#heroDesc` | `setEl('heroDesc', ...)` |
| `#currentPlantName` | `setEl(...)` |
| `#submitBtn` | `submitBtn.textContent = ...` |
| `#statusBadge` | `badge.textContent = ...` |
| `#filterLabel` | `labelEl.textContent = ...` |
| `#modalTitle` (users + schedule) | `setEl(...)` / `.textContent` |
| `#bulkTitle` · `#bulkGo` · `#assignedAreasSummary` | `setEl(...)` / `.innerHTML` |

**และ:** `apply()` ต้องมี equality guard (`if (el.textContent !== val)`) ทุกจุด
ไม่งั้น MutationObserver จะวนลูปไม่จบ — ตัว `_applying` flag ใช้ไม่ได้เพราะ
MutationObserver callback เป็น microtask ที่ทำงาน **หลัง** flag ถูกรีเซ็ตแล้ว

## 2.1 สิ่งที่ระบบทำได้ดี (ยืนยันจากโค้ดจริง)

| เรื่อง | หลักฐาน |
|---|---|
| RLS ครบทุกตาราง | 8/8 ตารางเปิด RLS · 25 policies (schema 19 + patches 4 + storage 2) |
| SQL Injection ปิดสนิท | ใช้ PostgREST query builder ทั้งหมด ไม่มี raw SQL · **`security definer` ทั้ง 9 ฟังก์ชันล็อก `search_path` ครบ** (จุดที่คนพลาดบ่อยที่สุดใน Postgres) |

## 2.2 ความเสี่ยงที่พบ (ยังไม่ได้แก้ทั้งหมด)

| # | ระดับ | เรื่อง | สาระ |
|---|---|---|---|

| 2 | 🟠 กลาง | Authorization | `auditor_id` ส่งจาก client — RLS `is_staff()` ยอมให้ admin/manager สร้างผลตรวจในชื่อคนอื่น (เสีย non-repudiation) |
| 3 | 🟠 กลาง | Headers | ไม่มี CSP / X-Frame-Options / Referrer-Policy เลย |
| 4 | 🟠 กลาง | Supply chain | `supabase-js@2` ไม่ pin version + ไม่มี SRI |

| 6 | 🟠 กลาง | API (BOPLA) | `schedules_auditor_update` กว้างเกินเจตนา — auditor แก้ `audit_date` และถอดคนอื่นออกจากทีมได้ |

| 8 | 🟡 ต่ำ | Logging | **แก้คะแนนย้อนหลังไม่มี log** — ไม่มี trigger บน `audit_details` · ไม่ log login ที่ล้มเหลว |
| 9 | 🟡 ต่ำ | Business logic | ไม่ล็อกผลตรวจหลัง submit — แก้ย้อนหลังได้ตลอด · ไม่กันตรวจซ้ำระดับ header |
| 10 | 🟡 ต่ำ | Info disclosure | `supabase/*.sql` ถูก deploy ขึ้นเว็บ — `storage_and_first_admin.sql` **เปิดเผย email admin** |
| 11 | 🟡 ต่ำ | File upload | ไม่เช็ค `file.size` ก่อนอ่าน · bucket `audit-photos` เป็น public |
| 12 | 🟡 ต่ำ | Error handling | ส่ง `error.message` จาก Postgres ให้ผู้ใช้เห็นตรง ๆ (31 จุด) · `console.log` 19 จุดใน production |
| 13 | ℹ️ | Business logic | `assigned_areas` ว่าง = เห็นทุกพื้นที่ (fail-open) |
| 14 | ℹ️ | Data exposure | ทุกคนที่ login อ่าน `profiles` ได้ทั้งตาราง รวม **email/role/department ของทุกคน** (เจตนา เพื่อ KPI) |
| 15 | ℹ️ | Performance | พบ `.limit()` แค่ 1 จุด (`getLogs` 300) — dashboard/history ดึงทั้งตาราง |

## 2.3 ยังตรวจไม่ได้ ต้องเปิด Supabase Dashboard เอง

| ที่ | ดูอะไร |
|---|---|
| Authentication → Policies | ความยาวรหัสผ่านขั้นต่ำ · leaked password protection |
| Authentication → Providers | เปิด email confirmation ไหม |
| Authentication → Sessions | JWT expiry · refresh rotation · inactivity timeout |
| Authentication → Rate Limits | ค่าปัจจุบัน |
| Storage → audit-photos | file size limit · MIME allowlist · public/private |
| Settings → API | CORS allowed origins |

**สำคัญ:** ต้องยืนยันว่า SQL ที่รันจริงใน DB ตรงกับไฟล์ใน `supabase/` — รายงานหัวข้อ B มีชุด query ให้รัน:

```sql
select tablename, rowsecurity from pg_tables where schemaname='public' order by tablename;
select tablename, policyname, cmd from pg_policies where schemaname='public' order by tablename, policyname;
```
คาดหวัง: `rowsecurity = true` ทั้ง 8 ตาราง · 23 policies ใน `public` (อีก 2 อยู่ใน `storage`)

## 2.4 แผนแก้ไข 3 ระยะ (ยังไม่เริ่ม)

**ระยะที่ 1 — ความเสี่ยงต่ำ ผลลัพธ์สูง (1–2 วัน)**
ตั้ง password policy · ลด JWT expiry เหลือ 30 นาที · ตั้ง storage limit ·
เพิ่ม `<meta>` CSP · เติม `'` ใน `escHtml()` + ครอบ `escAttr()` 5 จุด ·
ปิด `console.log` ใน production · ลบ email admin จาก SQL · ยืนยัน RLS ใน DB จริง

**ระยะที่ 2 — แก้ทั้ง DB และ client (1 สัปดาห์)**
เลิกเก็บ token เอง ใช้ `getSession()` · บังคับ `auditor_id = auth.uid()` ที่ DB ·
trigger log การแก้ `audit_details` · constraint วันที่/อีเมล ·
จำกัด BOPLA ของ `schedules` เป็น RPC · ย้ายการกรองพื้นที่ไป RLS · `safeError()`

**ระยะที่ 3 — ต้องคุยกับผู้ใช้งานก่อน (2–4 สัปดาห์)**
ล็อกผลตรวจ (`locked_at`) · submit เป็น RPC atomic · fail-closed ·
ปิด public bucket → signed URL · กันตรวจซ้ำ · ย้าย hosting เพื่อได้ HTTP header ครบ ·
ถอด inline `onclick` แล้วถอด `'unsafe-inline'` จาก CSP
