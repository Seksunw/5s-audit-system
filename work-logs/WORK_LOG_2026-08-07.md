## 2. ตรวจความพร้อม go-live ตอนเช้า — เจอปุ่มรีเซ็ตข้อมูลพังจริง (deployment gap)

ผู้ใช้ลองกดปุ่ม "รีเซ็ตข้อมูลระบบ" แล้วเจอ error `invalid input value for enum user_role: ""` — บั๊กเดิมที่ `patches.sql` บันทึกไว้ว่า "แก้แล้ว 5 ส.ค." แต่ **ตัวแก้ไม่เคยถูกรันขึ้น Supabase จริง** (ไฟล์ถูกต้องแต่ deploy ไม่ครบ)

**สาเหตุ:** `admin_reset_data()` เวอร์ชันที่รันอยู่จริงยังเป็นโค้ดเก่าที่ขาด `::text` cast (`coalesce(auth_role(), '')` แทนที่จะเป็น `coalesce(auth_role()::text, '')`) ทำให้ error ทันทีไม่ว่าใครกด (แม้ admin จริง) เทียบกับ `lock_audit()` ที่รันอยู่ถูกต้องอยู่แล้ว ยืนยันว่าเป็นแค่ฟังก์ชันนี้ฟังก์ชันเดียว

**แก้:** รัน `CREATE OR REPLACE FUNCTION admin_reset_data()` เวอร์ชันที่ถูกต้อง (ตรงกับ `patches.sql`) ผ่าน SQL Editor ตรง — ยืนยัน `pg_get_functiondef` ตรงกับไฟล์แล้ว ไม่มีการเปลี่ยน `patches.sql` เพิ่ม (ไฟล์ถูกต้องอยู่แล้วตั้งแต่แรก)

**บทเรียน:** patches.sql ไม่ได้เป็นแหล่งความจริงของ DB จริงเสมอไป — ต้องเช็ค `pg_get_functiondef`/live schema เทียบไฟล์เป็นระยะ โดยเฉพาะฟังก์ชันที่ระบุว่า "แก้แล้ว" ในคอมเมนต์

## 3. ตอบคำถามสถาปัตยกรรมก่อนใช้งานจริง (ไม่มีโค้ดเปลี่ยน)

- **ความจุ:** DB 12 MB / Storage 6.25 MB ตอนนั้น (จากเพดาน Free 500MB/1GB) · รูปเฉลี่ยจริง 128 KB/รูป (compressImage 1024px/q0.8 ทำงานดีกว่าคาด) · เจอรูปกำพร้าใน Storage 48/50 ไฟล์ (จากการทดสอบ/reset ที่ผ่านมา)
- **ระบบต้องออนไลน์ตลอดไหม:** GitHub Pages ออนไลน์เองอยู่แล้ว · Supabase Free tier auto-pause หลังไม่ใช้ 7 วัน (ต้องระวัง) · แอปไม่มี offline mode เลย — คำตอบระหว่างตรวจไม่ auto-save ลง localStorage ถ้าสัญญาณหลุดกลางคันจะหายหมด (ยังไม่ทำ ต้องขอเพิ่มทีหลังถ้าต้องการ)
- **แก้ไขผลตรวจได้ไหม:** ตาม policy DB แก้ได้ (auditor ก่อน submit / admin ตลอด) **แต่ในแอปยังไม่มี UI ให้กดแก้เลยสักหน้า** — ต้องทำผ่าน SQL Editor เท่านั้นตอนนี้

## 6. PDF ใบแจ้งพื้นที่ — รองรับพื้นที่เดียวตรวจโดยหลายคน

ตอนใช้งานจริงเจอเคส 1 พื้นที่มีคนตรวจมากกว่า 1 คนในรอบเดียวกัน ปัญหาเดิม: หัวข้อที่ตกซ้ำโชว์เป็น 2 การ์ดแยก (คำถามซ้ำเป๊ะ) แถวหัวใบโชว์ชื่อ "ผู้ตรวจ" แค่คนแรกที่เจอ

**ทำ design draft เป็น artifact เทียบหลายตัวเลือกก่อนแก้จริง** (รวมชื่อหัวใบ / chip ต่อการ์ด / merge การ์ดหัวข้อซ้ำ) — เลือกทำทั้งหมดรวมกัน:
- `getImprovementItems()` เพิ่ม `Criteria_ID` ให้ dedupe ได้
- `buildReportHTML()` เพิ่ม `groupByTopic()` — รวมหัวข้อซ้ำ (criteria เดียวกัน) เป็นการ์ดเดียว badge ใช้คะแนนต่ำสุด พร้อม tag "ตรวจซ้ำ N ครั้ง" แยกกลุ่ม remark/รูปตามคนตรวจในการ์ดเดียว
- บรรทัด "ผู้ตรวจ" ที่หัวใบ + ลายเซ็นรวมชื่อทุกคนที่มีส่วนในพื้นที่นั้น (ไม่ใช่คนแรกที่เจอ)
- KPI/จำนวนข้อที่ตกนับจากหัวข้อ dedupe แล้ว ไม่ใช่แถวดิบจาก DB

ทดสอบด้วย standalone harness (stub browser globals แล้ว `require()` เรียก `buildReportHTML()` ตรงๆ) ก่อน commit

**ปรับเพิ่มอีกรอบ:** ผู้ใช้ขอเอาชื่อ/คะแนนผู้ตรวจต่อคอมเมนต์ออก (ทั้งการ์ดเดี่ยวและการ์ด merge) เหลือแค่คอมเมนต์+รูป — เก็บ "ตรวจซ้ำ N ครั้ง" กับบรรทัดผู้ตรวจที่หัวใบไว้ (เป็นข้อมูลระดับพื้นที่ ไม่ใช่ต่อคอมเมนต์) ลบ CSS ที่ไม่ใช้แล้ว (`who-chip`/`src-head`/`src-avatar` ฯลฯ)

## 9. บั๊กใหญ่: งานมอบหมายค้าง ทั้งที่ auditor ตรวจเสร็จจริงแล้ว

**อาการที่รายงาน:** auditor ตรวจงานที่มอบหมายครบ ผลขึ้นในประวัติปกติ แต่ "งานที่ได้รับมอบหมาย" ยังค้างไม่ขยับ

**Root cause:** มี 2 ทางเข้าหน้าตรวจ — ผ่าน "งานที่ได้รับมอบหมาย" (`startAssignedAudit()`) ส่ง `scheduleId` ถูกต้อง แต่ผ่านทางปกติ **Plant → Area → กดตรวจ** (`selectArea()`) **ไม่เคยส่ง `scheduleId` เลย** ทั้งที่การ์ดพื้นที่โชว์ badge รอบ/วันที่อยู่แล้ว (มีข้อมูลแค่ไม่ถูกส่งต่อ) ผลตรวจเลยได้ `schedule_id = NULL` — ไม่นับเข้า progress ของงานมอบหมาย (แม้ผลตรวจเองถูกต้องสมบูรณ์)

เช็คทั้งระบบเจอ 2 คนโดนจริง: **คุณเล็ก** (6 พื้นที่) + **คุณแหวน** (1 พื้นที่) รวม 7 audit_headers ที่ `schedule_id`/`audit_round` เป็น NULL ทั้งที่มีงานมอบหมายจริงรออยู่

**แก้ข้อมูล:** backfill `schedule_id`+`audit_round` ให้ทั้ง 7 รายการ (ตรวจสอบก่อนว่าอยู่ใน `auditor_ids` ของ schedule จริง) แล้ว recompute `schedules.status` เอง (trigger `sync_schedule_status` ทำงานแค่ตอน INSERT/DELETE หรือแก้ `locked_at`/`status` ไม่ทำงานตอนแก้ `schedule_id` เฉยๆ) — schedule เปลี่ยนจาก pending→completed ครบ 7 รายการ (รวม completed 1→9 จาก 16 schedule ทั้งหมด)

**แก้โค้ดกันไม่ให้เกิดซ้ำ:** เพิ่ม `data-schedule-id` ในการ์ดพื้นที่ + ส่งต่อผ่าน `selectArea()`/`selectAreaFromEl()` เหมือนที่ `startAssignedAudit()` ทำอยู่แล้ว

**Commit:** `dd7abf8` — fix(audit): carry schedule_id when starting audit from Plant->Area flow

## ค้าง / ควรทำต่อ

- Leaked Password Protection ยังปิดอยู่ (เปิดเองใน Supabase Dashboard เท่านั้น)
- รูปกำพร้าใน Storage 48 ไฟล์ (~6MB) จากการทดสอบ — ยังไม่ได้เคลียร์
- ไม่มี UI แก้ไขผลตรวจย้อนหลังในแอป (ต้องผ่าน SQL Editor) — เสนอทำแล้ว ยังไม่ได้รับคำตอบ
- ไม่มี auto-save คำตอบระหว่างตรวจ (เสี่ยงหายถ้าสัญญาณหลุดกลางคัน) — เสนอทำแล้ว ยังไม่ได้รับคำตอบ
- `isStaff` client-side ยังเช็ค role `manager` เก่า (S1 — ความเสี่ยงต่ำ DB ปลอดภัยอยู่แล้ว)
