## 2. 🐛 Bug ที่ 1 — เทียบ enum กับ `''`

**อาการ:** กดปุ่มแล้วขึ้น `invalid input value for enum user_role: ""`

**โค้ดเดิม** (`patches.sql:161` และ `schema.sql:336` — ทั้ง 2 ไฟล์):

```sql
if coalesce(public.auth_role(), '') <> 'admin' then
  raise exception 'permission denied: admin only';
end if;
```

**สาเหตุ:** `auth_role()` คืนชนิด `user_role` (enum) · `coalesce()` ต้องการให้ argument
ทุกตัวชนิดเดียวกัน → Postgres แปลง `''` เป็น `user_role` → **`''` ไม่ใช่ค่าที่ถูกต้องของ enum** จึงล้ม

**ผลกระทบ:** ฟังก์ชันล้มที่บรรทัดแรกเสมอ **ไม่ว่าจะเป็น admin หรือไม่**
→ ปุ่มรีเซ็ตใช้งานไม่ได้เลยตั้งแต่วันที่สร้าง (อธิบายได้ว่าทำไมไม่มีตาราง `*_backup` มาก่อน)

**แก้:**

```sql
if coalesce(public.auth_role()::text, '') <> 'admin' then
```

cast เป็น `text` ก่อน → กลายเป็นการเทียบ text กับ text ไม่ต้องแปลง `''` เป็น enum

> **หมายเหตุ:** จุดอื่นที่ใช้ `auth_role() = 'admin'` (RLS policies, `is_staff()`) **ปลอดภัย**
> เพราะ `'admin'` เป็นค่าที่มีอยู่ใน enum จริง · ปัญหาอยู่ที่ `''` เท่านั้น

## 3. 🐛 Bug ที่ 2 — Supabase บล็อก `delete from storage.objects`

**อาการ:** หลังแก้ bug 1 กดปุ่มอีกครั้ง ขึ้น
`Direct deletion from storage tables is not allowed. Use the Storage API instead.`

**สาเหตุ:** Supabase เพิ่มการบล็อก `DELETE` ตรงบน `storage.objects` แล้ว
บรรทัดนี้ในฟังก์ชันจึง raise:

```sql
delete from storage.objects where bucket_id = 'audit-photos';
```

**ข่าวดี — transaction rollback ทำงานถูกต้อง**

ลำดับในฟังก์ชันคือ: เช็คสิทธิ์ → นับ → สร้าง backup → **truncate** → **ลบรูป (ล้มที่นี่)**
plpgsql ทำงานใน transaction เดียว → raise แล้ว **rollback ทั้งหมด**

ยืนยันด้วย query หลัง error: `41 · 2770 · 14 · 20 · 0` — **ข้อมูลครบ ไม่มีตารางสำรองค้าง** ✓

**แก้ — ย้ายการลบรูปไปทำที่ client ผ่าน Storage API**

เอาบรรทัดลบรูปออกจาก SQL ทั้ง 3 ไฟล์ (`patches.sql` · `schema.sql` · `reset_test_data.sql`)
พร้อมคอมเมนต์เตือนไม่ให้ใส่กลับ · แล้วเพิ่มฟังก์ชันใหม่ใน `js/app.js`:

```js
async purgeAuditPhotos() {
  const B = CONFIG.STORAGE_BUCKET;
  let removed = 0, failed = 0;

  const walk = async (prefix) => {
    const { data:items, error } = await _sb.storage.from(B)
      .list(prefix, { limit: 1000, sortBy: { column:'name', order:'asc' } });
    if (error) { failed++; return; }

    const files = [], dirs = [];
    (items || []).forEach(it => {
      // โฟลเดอร์ไม่มี metadata / id
      if (it.id === null || it.metadata == null) dirs.push(it.name);
      else files.push(prefix ? `${prefix}/${it.name}` : it.name);
    });

    for (let i = 0; i < files.length; i += 100) {          // ลบชุดละ 100
      const chunk = files.slice(i, i + 100);
      const { error: rmErr } = await _sb.storage.from(B).remove(chunk);
      if (rmErr) failed += chunk.length; else removed += chunk.length;
    }
    for (const d of dirs) await walk(prefix ? `${prefix}/${d}` : d);
  };

  await walk('');
  return { removed, failed };
}
```

**จุดที่ต้องระวังในการเขียน:**

| เรื่อง | เหตุผล |
|---|---|
| ต้องเดินซ้ำทุกโฟลเดอร์ | `list()` คืนไฟล์เฉพาะชั้นเดียว แต่ path จริงคือ `audit/xxx.jpg` |
| แยกไฟล์กับโฟลเดอร์ด้วย `id === null \|\| metadata == null` | Supabase คืนโฟลเดอร์เป็น item ที่ไม่มี metadata |
| ลบเป็นชุดละ 100 | กัน payload ใหญ่เกิน |

`resetData()` ลบรูปก่อนแล้วค่อยเรียก RPC — ถ้าลบรูปล้มก็ยังรีเซ็ต DB ต่อได้ แค่รายงานจำนวนที่ลบไม่ได้
toast แสดงผลรูปด้วย: `รีเซ็ตแล้ว: ประวัติ 41 · มอบหมาย 14 · รูป 20 (สำรองไว้ที่ *_backup)`

## 5. 🔑 บทเรียนสำคัญที่สุดของวันนี้

> **"โค้ดมีอยู่" ≠ "ทำงานได้"**

`admin_reset_data()` ผ่านการตรวจมาแล้ว **2 รอบ**:

1. รายงานประเมินความปลอดภัย 16 หัวข้อ (3 ส.ค.) — อ่านฟังก์ชันนี้ทั้งตัว ชมว่า
   "ออกแบบดี เช็คสิทธิ์ในตัวฟังก์ชัน ไม่พึ่ง client"
2. งานล็อกตาราง `*_backup` (4 ส.ค.) — แก้ไขในฟังก์ชันนี้โดยตรง ตรวจ `pg_proc` ยืนยันว่าอัปเดตแล้ว

**ทั้ง 2 รอบไม่เจอ bug** เพราะ:

- Bug 1 ต้อง **รัน** ถึงจะเห็น — static analysis อ่านโค้ดแล้วดูสมเหตุสมผล
- Bug 2 เป็นการเปลี่ยนแปลงฝั่ง Supabase ที่เกิดขึ้นภายหลัง — ไม่มีใน SQL ตัวเอง
- การตรวจว่า "ฟังก์ชันอัปเดตแล้ว" (เช็ค `prosrc`) ยืนยันแค่ **ข้อความในฟังก์ชัน** ไม่ได้ยืนยันว่า **เรียกได้**

**สิ่งที่ควรทำต่อจากนี้:**

- ปุ่ม/ฟังก์ชันที่ทำลายข้อมูล ควร **ทดสอบบน staging จริง** ไม่ใช่แค่อ่านโค้ด
- `Success` ของ SQL Editor และ `prosrc like '%...%'` **ไม่ใช่หลักฐานว่าใช้งานได้**
  ต้องเรียกฟังก์ชันจริงหนึ่งครั้ง
- ค่าที่ควรมี: smoke test เรียก RPC ทุกตัวหลัง deploy migration

# ส่วนที่ 2 — 🔐 จัดระเบียบสิทธิ์ให้เหลือ 3 roles + ล็อกผลตรวจ

## 8. การตัดสินใจเชิงนโยบาย

ระบบเดิมมี 4 roles ใน enum แต่ **`manager` กับ `area_manager` ไม่มีความหมายจริง**
(`area_manager` ไม่ถูกอ้างใน policy ไหนเลย · `manager` ถูก UI บล็อกแต่ RLS อนุญาต)

**ตัดสินใจ:** ใช้ 3 roles

| role | ความหมาย |
|---|---|
| 👑 `admin` | จัดการทุกอย่าง · แก้ผลตรวจได้ตลอด |
| 📋 `auditor` | ตรวจ 5ส · **ดูผลตรวจทั้งบริษัท** (Dashboard/ranking มีความหมายครบ) · แก้ผลตัวเองไม่ได้หลัง submit |
| 👁️ `viewer` | ผู้บริหาร — ดูได้ทุกอย่างรวม remark/รูป แต่ **ตรวจไม่ได้ แก้ไม่ได้** |

## 9. ⚠️ ข้อจำกัด: Postgres ลบค่าออกจาก enum ไม่ได้

มีแต่ `add value` ไม่มี `drop value` · การลบต้องสร้าง type ใหม่ + แปลงคอลัมน์
+ drop/create policy ทุกตัวที่อ้าง `user_role` = งานใหญ่เสี่ยงสูง

**วิธีที่เลือก:** `add value 'viewer'` แล้ว **เอา `manager`/`area_manager` ออกจาก dropdown**
→ เลือกไม่ได้อีก · คนที่เป็น role เก่าอยู่ยังใช้งานได้ต่อ (ได้สิทธิ์เท่า `auditor`) ไม่พัง

> ⚠️ `alter type ... add value` ต้อง **รันแยกก่อน** — ค่า enum ที่เพิ่งเพิ่มใช้ใน
> transaction เดียวกันไม่ได้ (จึงทำเป็นคอมเมนต์ในส่วน G0 ให้ uncomment รันเดี่ยว)

## 10. SQL — เพิ่มส่วน G ใน `patches.sql`

| ส่วน | ทำอะไร |

## 17. 🐛 Bug — `role` ถูกแช่ไว้ใน localStorage ตอน login

**อาการ:** เปลี่ยน role คนหนึ่งเป็น Viewer แล้ว เครื่องนั้นยังเห็นปุ่มตรวจ

**สาเหตุ:** `Session.save()` เขียน `{token, user}` ลง localStorage ตอน login
`Session.load()` อ่านกลับมาตรง ๆ · **ไม่มีจุดใดดึง role ใหม่จาก DB เลย**

```js
// เดิม — role มาจาก localStorage เท่านั้น
load() {
  const data = JSON.parse(localStorage.getItem(CONFIG.SESSION_KEY) || 'null');
  if (data) { AppState.token = data.token; AppState.user = data.user; return true; }
}
```

→ `isViewer()` อ่าน `AppState.user.role` = ค่าเก่า → guard ไม่ทำงาน
→ **admin เปลี่ยน role ให้คนที่กำลังล็อกอินอยู่ ไม่มีผลจนกว่าคนนั้นจะ logout**

**แก้ — เพิ่ม `Session.refreshRole()`** เรียกใน 5 จุด
(`initHome` · `initMyTasks` · `initPlant` · `initArea` · `initAudit`)

```js
async refreshRole() {
  const uid = (AppState.user || {}).userId;
  if (!uid) return null;
  const { data, error } = await _sb
    .from('profiles').select('role,status').eq('id', uid).single();
  if (error || !data) return null;

  // ถูกระงับการใช้งานระหว่างที่ยังล็อกอินอยู่ → เตะออก
  if (data.status && data.status !== 'active') {
    Session.clear(); navigate('index.html'); return null;
  }

  const fresh = MAP.role[data.role] || data.role;
  if (fresh !== AppState.user.role) {
    AppState.user.role = fresh;
    localStorage.setItem(CONFIG.SESSION_KEY,
      JSON.stringify({ token: AppState.token, user: AppState.user }));
  }
  return currentRole();
}
```

**ได้ของแถม:** ถ้า admin เปลี่ยน status เป็น `inactive` ระหว่างที่คนนั้นยังใช้งานอยู่
เดิม**ใช้งานต่อได้เรื่อย ๆ** ตอนนี้ถูกเตะออกทันทีที่เปลี่ยนหน้า
